# 最终建议

## 对验收问题的回答

1. **C 能处理 V2 的真实 GIS 困难案例吗？** 对 REAL-000 和 REAL-081 的单轮预算优化可以：两组 C Harness 结果均匹配独立 V2 Oracle。它不能完成 T04 所要求的 Greedy/MIP 差异解释，因为 B 解释响应只含诊断。
2. **复杂多轮请求能转成 B 参数吗？** 已覆盖的预算更新、预算/步行字段绑定、用户改候选后重优化、停用场所和缺参追问通过。预算撤销恢复是 Session/normalizer 状态回归，不能当作完整模型对话结果。
3. **Skill Graph 改善成功率或调用效率了吗？** 尚无因果结论。B 的所有可用任务路径都会执行 Graph；仅观察到一次重复运行 3/8 节点缓存命中及 36.9% 墙钟减少。
4. **Verifier 超出求解器检查带来收益吗？** 有有限的安全收益：C 能拒绝跨 Session result_id、错误 Scenario/验证状态和 DEMO_ONLY 过度声明。它没有独立复算 MIP 最优性，不能代替数学 Oracle。
5. **Harness 恢复有效吗？** T14 的错误结果被挡住，后续全新请求恢复成功；恢复是测试方人工重发，不是 Harness 自动回滚/重试。参数状态也未见错改。
6. **端到端主要瓶颈在哪？** 当前是 B 的任务解释接口覆盖度（T04），然后是 C 仍待纳入正式分支的字段绑定/Session 边界修复与真实 LLM/MCP 端到端缺失。数学求解器不是已测任务的瓶颈。
7. **下一步修改哪个模块？** 优先给 B 增加明确的 `compare_greedy_mip` 任务/响应契约，返回两边的目标值、选项、预算可行性和差值，并为它固定独立 Oracle 回归。随后由代码审查将 C 的隔离修复整理成可审阅补丁；本轮不自动合并。

## 建议的后续验收

- 对 B Greedy/MIP 解释契约补充 REAL-000、REAL-081 和 V2 合成 trap 的独立 Oracle 测试。
- 由项目维护者审查 `reports/isolation_patch.diff`，决定是否把 C 的 session membership、字段绑定、预算词形和 DEMO_ONLY 声明门禁修复纳入正式 C。
- 在无收费调用的前提下配置可用真实 LLM 后再测 A/B/C/D；为 B 提供显式 graph-off 或独立测试入口，保证消融可控。
- 安装 MCP SDK 后运行 stdio/HTTP 真实客户端测试；当前只验证了本地应用 API 路径。
- 保持候选项最多 12；大规模合成性能问题应另开有明确公共 API 契约的实验。

## 边界

本轮没有修改正式 B、没有改写正式 C 源、没有 Git merge/commit/push，也未调用收费 API。V3 报告中的规划值均为 DEMO_ONLY；合成场所增量是人为假设，不应作为现实应急建议。
