# Composite Disaster Recovery: Design and Handoff

## Baseline and scope

Implementation baseline: `origin/feat/map-first-resilience-ui` at
`5f816536e7025300c9739b49a57836e3f7b14635`.

This change is limited to Module B and Module C. It adds a bounded recovery
workflow and its C Harness integration. It does not modify `frontend/`, Module
A data/configuration, `merge_data/`, the LP/MIP solver, or the existing verifier
mathematics. The existing single-stage routes and S01-S12/C01-C05 contracts
remain available; the recovery API is additive.

## Existing architecture review

- B already exposes registered S01-S12 skills and C01-C05 task templates.
  `execute_task()` validates a registered task, runs the required skills,
  persists a result and trace, and applies the existing assignment/budget
  verifiers.
- A normal B `TaskRequest` represents one task type. It cannot carry an
  auditable baseline → damage → diagnose → recover → compare contract across
  multiple scenarios.
- C owns the authoritative full scenario snapshot and session-scoped result
  registry. It performs preflight/postflight checks and records tool-call/task
  traces. Existing compare construction previously omitted common effective
  parameters from explicit rows; damage-plus-impact language could also lose
  the shutdown intent during routing.
- B scenario IDs are persisted separately from C session IDs. The workflow
  therefore creates explicit B scenario IDs and binds them to stage result IDs;
  C commits the actual recovered B scenario after postflight succeeds.

## Responsibilities and API

`POST /planning/disaster-recovery` accepts `DisasterRecoveryRequest`; the
existing `/planning/tasks`, `/planning/stress-tests`, and `/planning/comparisons`
contracts are unchanged. The request contains the user's goal, source identity,
baseline snapshot, explicit damaged shelter IDs, confirmed budget, and at most
12 supplied recovery options. No options or costs are generated by the server.

The B `CompositeWorkflowPlanner` owns the finite stage state machine. It
advances only after the previous stage produced a publishable result. Each
assessment/optimization is delegated to the existing `execute_task()` path and
registered skills. S05 diagnosis is read from the damaged assessment trace.
There is no caller-defined DAG or second solver.

The C Harness owns dialogue, per-session state, request construction and an
independent orchestration/integrity postflight check. C passes the same region,
data version, demand ratio and walk threshold through the whole chain. Baseline
keeps previously confirmed disabled facilities; damage adds only the explicit
shutdowns; recovery retains that damaged state and adds the confirmed budget.
Options targeting disabled or unknown facilities are refused.

## State and publication rules

- Immutable during a run: source identity, region and data version.
- Inherited: demand ratio, walking threshold, and already confirmed disabled
  shelters.
- Explicit stage changes: shutdowns in Damage and budget/options in Recovery.
- Missing budget/options end the B workflow after diagnosis as `NEEDS_INPUT`
  without submitting the recovery optimizer. C normally asks for the missing
  slots before submitting the composite task.
- Invalid options, stage verifier failures, parameter drift, result misbinding,
  or source mismatch stop downstream work and return an auditable partial
  contract. No result is committed by C until postflight passes.
- `OPTIMAL` and `FEASIBLE` remain distinct. DEMO and synthetic results remain
  `PASS_DEMO`; they are never described as field-verified.

The result contains the `RecoveryTaskContract`, ordered stage records, parent
scenario IDs, effective parameter snapshots, input result IDs, branch decisions,
constraint checks, verifier statuses and a shared execution trace ID. The C
projection keeps compact stage links in the normal result summary; full B
results remain available through the existing session-scoped result reader.

## Verification plan and limits

Tests use the existing `tests/module_b/fixtures/toy_case.json` fixture to run the
real B assignment LP, budgeted MIP and verifiers through the real FastAPI app.
That source is `SYNTHETIC_FIXTURE`, not Module A data. A GIS run still requires
an allowlisted Module A source in the exact admitted version. This change does
not claim real-world validation, add a frontend, or run an external/paid LLM.

Acceptance commands:

```powershell
python -m pytest tests/module_b -q
python -m pytest tests/module_c -q
python -m compileall -q backend agent
```

## Module D / evaluation handoff

Consumers should use `task_type=disaster_recovery`, then read `status`,
`stage_results`, `branch_decisions`, `constraint_checks`, `verification_results`,
the per-stage `result_id`/`input_result_ids`, `execution_trace_id`, and B skill
trace. `NEEDS_INPUT` is not a completed plan. A consumer must preserve
`data_status`, solver status and verifier status, and must not infer that
`PASS_DEMO` means operational acceptance. The full API schema is discoverable
from `/openapi.json` and workflow metadata from `/planning/capabilities`.
